설계안 — 결재권 위임

2026-10-21 · 무대는 재고 관리 · 2026-10-20 「방법 B(별도 표)」 결정 위에 세움 · 2026-10-21 코드 실측 반영

풀려는 문제 — 결재권자가 출장·휴가로 자리를 비우면 그 건이 선다. 2026-10-20 에 지금 실제로 일이 멈추고 있는 것을 확인했습니다.

조사로 드러난 것 — 설계를 가르는 다섯

① 🔴 위임은 지금 코드가 기대고 있는 전제를 깬다

결재 단계 줄에는 「누가 눌렀는가」를 적는 칸이 없습니다. 그 줄에 적힌 사람만 쓸 수 있게 DB 조건으로 묶어 두었기 때문에, 「적힌 사람 = 누른 사람」이 언제나 참이었습니다.

위임이 들어오면 B 가 A 의 이름이 적힌 줄을 누릅니다. 전제가 깨지므로 칸을 더해야 합니다. → 마이그레이션이 필요합니다.

② 🔴 판정하는 자리가 넷이고, 시험은 그중 운영이 안 쓰는 하나만 본다

자리무엇빠뜨리면
집행decidePartIssueApproval 의 DB 조건절 — 진짜로 막는 유일한 울타리위임이 아예 안 먹는다
목록「내가 결재할 건」을 고르는 조회 대리인 화면에 그 건이 안 보인다
알림 종머리말 종 숫자를 세는 조회 (포털로도 나간다) 🔴 대리인에게 종이 안 울린다 — 가 보면 있는데 알림이 없다
규칙 사본mayDecidePartIssueStep 🔴 시험만 통과하고 운영은 그대로 막는다
🔴 네 번째가 함정입니다. 「규칙이 적힌 곳은 하나」라고 주석에 적혀 있지만, 실제로는 같은 규칙이 두 곳에 손으로 적혀 있고 운영은 조건절 쪽을 씁니다. 그 함수를 부르는 곳은 시험뿐인 것을 직접 확인했습니다.

③ 🔴 열쇠를 틀리면 2026-10-15 에 났던 장애가 재현된다

결재자는 포털 번호로, 신청자는 이 시스템 사용자 번호로 가립니다. 서로 다른 열쇠입니다. 위임 표는 포털 번호로 적습니다.

④ 🔵 쉬워지는 것 — 절차 고르기에 분기가 없다

절차는 「부품 불출」 하나 고정이고 가장 최근 판을 씁니다. 고객사별·금액별 분기가 코드 어디에도 없습니다. 「어느 절차가 붙나」를 위임이 신경 쓸 필요가 없습니다.

⑤ 🔴 「결재 중」에 갇힐 위험 — 이 설계가 피하는 방식

어제 만든 규칙이 「결재건이 움직이면 반드시 네 길 중 하나로 신청 상태를 되돌린다」로 엄격하게 묶여 있습니다. 새 길이 생기면 그 넷 어디에도 안 들어가 신청이 영영 멈춥니다.

🔵 이 설계는 새 길을 만들지 않습니다. 위임은 누가 누르느냐만 바꿉니다 — 결재건의 상태 흐름은 한 글자도 바뀌지 않습니다. 그래서 네 갈래가 그대로 유효합니다.
🔴 그러므로 「위임 해제로 인한 강제 반려」 같은 것을 만들지 않습니다. 그것이 바로 갇힘을 만드는 길입니다.

설계 — 표 하나와 칸 둘

새 표 approval_delegations

id                uuid        PK
delegator_sub     text        NOT NULL   -- 결재권자 (포털 번호)
delegator_name    text        NOT NULL   -- 그때의 이름 (사본)
delegate_sub      text        NOT NULL   -- 대신할 사람 (포털 번호)
delegate_name     text        NOT NULL
starts_at         timestamptz NOT NULL
ends_at           timestamptz NOT NULL   -- 🔴 반드시 적는다
reason            text        NOT NULL DEFAULT ''
created_by_sub    text        NOT NULL   -- 누가 이 위임을 만들었나
created_by_name   text        NOT NULL
created_at        timestamptz NOT NULL DEFAULT now()
revoked_at        timestamptz NULL       -- 되돌림. 🔴 줄을 지우지 않는다
revoked_by_sub    text        NULL
revoked_by_name   text        NULL

CHECK  ends_at > starts_at
CHECK  delegate_sub <> delegator_sub        -- 자기에게 위임 금지
INDEX  (delegate_sub, revoked_at, ends_at)  -- 「내가 누구의 대리인인가」를 읽는 길
🔵 이름을 함께 적는 까닭은 결재선 표가 이미 그렇게 하고 있는 것과 같습니다 — 사람 명부가 이 시스템에 없고 A/S 에서 받아 오기 때문에, 나중에 그 사람이 없어지거나 이름이 바뀌어도 그때 누구였는지가 남아야 합니다.
🔴 결재 종류별로 나누지 않습니다 (칸을 두지 않습니다)
지금 결재 종류는 「부품 불출」 하나뿐이라, 종류 칸을 둬도 모든 줄이 같은 값이 되어 아무것도 가르지 못하면서 화면과 시험만 늘립니다. 그리고 사람이 자리를 비우는 것은 사람의 사정이지 결재 종류의 사정이 아닙니다 — 출장을 가면 모든 결재를 못 합니다.
🔵 [출하승인]이 들어와 종류가 둘이 되는 날 칸을 더합니다. 위임은 기간이 짧아 그때 살아 있는 줄이 거의 없으므로 나중에 더해도 싸게 끝납니다.

칸 더하기 stock_issue_approval_steps 에 둘

decided_by_sub    text  NULL   -- 실제로 누른 사람
decided_by_name   text  NULL
🔴 이 칸의 값은 세 가지 뜻을 가집니다. 주석에 못 박아야 합니다.
  • NULL — 이 칸이 생기기 전에 결재된 옛 줄입니다. 「본인이 눌렀다」는 뜻이 아닙니다.
  • decided_by_sub = approver_sub — 본인이 눌렀습니다.
  • decided_by_sub <> approver_sub — 대리인이 눌렀습니다.
🔵 앞으로는 본인이 눌러도 언제나 적습니다. 비워 두면 「본인」과 「옛날 것」이 같은 모양이 되어 갈 수 없습니다.

다섯 물음에 대한 답

1. 기간을 정하는가?

🔴 반드시 끝을 적게 합니다. 「깜빡하면 영영 남는다」가 방법 A(절차 안의 사람을 바꿔치기)를 버린 까닭이었는데, 끝 없는 위임은 같은 문제를 그대로 다시 만듭니다.

2. 되돌릴 수 있는가?

🔵 있습니다. 다만 줄을 지우지 않고 되돌린 시각과 사람을 찍습니다 — 지우면 「그 기간에 누가 대리였는지」가 기록에서 사라져, 그 사이에 난 결재를 나중에 설명할 수 없습니다.

3. 위임받은 사람이 또 위임할 수 있는가?

🔵 있습니다 — 다만 권한은 이어지지 않습니다. 2026-10-21 구현 중 바로잡음: 처음에는 「안 된다」로 적었는데, 그 까닭(고리가 생긴다 · 책임자가 흐려진다)이 판정에서 이미 해결됐습니다. delegatorSubsFor 가 이어 붙이지 않으므로 A→B 와 B→C 가 있어도 C 는 A 의 결재권을 얻지 못합니다. 한 겹씩 명시적으로만 넘어갑니다.
🔴 그런데 만드는 쪽에서까지 막으면 남의 대리인이 된 사람은 자기 결재권조차 맡길 수 없게 됩니다 — B 도 출장을 갈 수 있습니다. 그래서 만들 때는 막지 않습니다. 안전은 판정이 지킵니다.

4. 위임 중에 원래 결재권자가 결재하면?

🔵 됩니다. 위임은 권한을 넘기는 것이 아니라 늘리는 것입니다. 출장 중에 전화로 처리하는 일이 실제로 있습니다. 🔴 원래 사람을 막으면 대리인까지 자리를 비웠을 때 아무도 못 누릅니다 — 지금 풀려는 문제가 그대로 돌아옵니다.

5. 누가 눌렀고 누구 자리였는지가 둘 다 남는가?

🔵 남습니다. 단계 줄에 approver_*(누구 자리인가)와 decided_by_*(누가 눌렀나)가 나란히 남고, 변경 이력에도 실제 행위자가 적힙니다. 화면에는 「김○○ 결재 (이○○ 대리)」로 보입니다.

판정을 어떻게 바꾸는가

지금: 그 줄의 결재자 번호 = 내 번호
바뀐 뒤: 그 줄의 결재자 번호 = 내 번호 또는 내가 지금 그 사람의 대리인이다

🔵 조건절 안에 다른 표를 끌어들이지 않기를 권합니다. 「내가 지금 누구의 대리인인가」를 먼저 한 번 읽어 번호 목록을 만들고, 그 목록을 조건에 넣는 편이 읽기 쉽습니다. 목록은 보통 비어 있거나 한둘입니다.
🔴 읽는 것과 쓰는 것이 같은 트랜잭션 안에 있어야 합니다 — 사이에 위임이 끝나면 「목록에는 있는데 실제로는 권한이 없는」 순간이 생깁니다.
🔴 네 자리를 전부 고쳐야 하고, 그중 「규칙 사본」은 지금 운영이 쓰지 않습니다. 이 조각에서 그 두 벌을 한 벌로 합치기를 권합니다 — 합치지 않으면 위임을 넣은 뒤에도 시험은 통과하는데 운영은 다르게 도는 상태가 그대로 남습니다.

  • 울타리: 역할을 묻지 않습니다. 로그인한 사람이면 누구나 들어오되, 만들 수 있는 것은 자기 결재권의 위임 하나뿐입니다 — delegator_sub 는 화면이 보내는 값이 아니라 서버가 세션에서 꺼내 넣습니다. 🔴 화면이 보낸 값을 그대로 믿으면 남의 결재권을 넘기는 요청을 만들 수 있습니다.
  • 🔵 결재선에 안 든 사람이 위임을 만들어도 아무 효과가 없습니다(넘길 권한이 없으므로). 그래서 들어오는 사람을 따로 가릴 필요가 없습니다.
  • 되돌리기도 본인만입니다. 자기가 만든 위임만 되돌릴 수 있습니다.
🔵 관리자에게는 보는 것만 열어 두는 편이 좋습니다 — 지금 살아 있는 위임 목록을 설정 화면에서 읽을 수 있으면, 결재가 왜 그 사람에게 갔는지 설명할 수 있습니다. 🔴 읽기만입니다. 만들기·되돌리기는 열지 않습니다.

시험으로 물어야 할 것

  • 기간 밖(시작 전 · 끝난 뒤)이면 대리가 안 된다
  • 되돌린 위임은 그 즉시 안 된다
  • 🔴 원래 결재권자는 위임 중에도 된다 (물음 4)
  • 🔴 권한이 두 겹으로 이어지지 않는다 — A→B·B→C 가 있어도 C 는 B 의 자격만 얻고 A 의 것은 못 얻는다. 🔵 만드는 것은 막지 않는다(물음 3)
  • 🔴 남의 단계는 여전히 못 누른다 — 위임이 「아무나 되는 문」이 되지 않았는지
  • 🔴 관리자라고 대신 누를 수 없다 — 지금 시험이 지키고 있는 것이 그대로 유지되는지
  • 🔴 남의 결재권을 넘기는 위임을 만들 수 없다 — 화면이 보낸 delegator_sub 를 서버가 무시하고 세션 값을 쓰는지. 관리자도 못 만든다
  • 🔴 남이 만든 위임을 되돌릴 수 없다
  • 🔴 알림 종 숫자가 대리인에게 늘어난다 — 목록과 같은 수인지
  • 대리가 누르면 decided_by_* 가 대리인으로, 본인이 누르면 본인으로 적힌다

안 하는 것

  • 절차 안의 사람을 바꿔치기하지 않습니다(방법 A) — 2026-10-20 결정
  • 결재건의 상태 흐름을 건드리지 않습니다 — 「결재 중」에 갇히는 사고를 만들지 않으려는 것입니다(⑤)
  • 위임 해제로 진행 중인 결재를 되돌리지 않습니다 — 이미 난 결재는 그때 유효했던 것입니다
  • 결재 종류별로 나누지 않습니다 — 종류가 하나뿐입니다
  • 위임을 만드는 것을 두 겹이라고 막지 않습니다 — 권한이 이어지지 않는 것은 판정이 지킵니다(물음 3)
