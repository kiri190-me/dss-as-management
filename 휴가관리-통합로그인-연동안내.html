DSS 휴가 관리 — 통합로그인 연동 안내

이남준 님께 · 2026-09-21 · A/S · 계측기 · 개선요청 · PO 를 붙이며 겪은 것을 정리했습니다

저장소를 받아 살펴보았습니다. 연동에 필요한 것과, 저희가 실제로 밟았던 함정을 적습니다. 코드는 건드리지 않았습니다(푸시 권한도 없고, 같은 파일을 둘이 고치면 충돌해서입니다).

좋은 소식부터 — 생각보다 붙이기 쉬운 구조입니다.

  • jose 가 이미 설치돼 있습니다
  • web_users.auth_sub 칸이 이미 있습니다 — 포털 id 를 담을 자리가 준비돼 있습니다
  • 스키마를 안 바꿔도 됩니다(아래 3번 참조)
  • dev-login.ts 첫 줄에 「dss-auth OIDC 연결 시 폐기 대상」이라고 적어 두셔서, 갈아끼울 자리가 이미 정해져 있습니다

0🔴 먼저 아셔야 할 것 — 지금 계정이 전부 새로 만들어집니다

이것이 이 문서에서 가장 중요합니다.

지금 dev-login.ts 는 이름을 해시해서 가짜 UUID 를 만들어 auth_sub 에 넣습니다 (fakeSubFor()). 통합로그인의 진짜 sub 는 포털이 발급한 완전히 다른 값입니다.

그래서 그냥 갈아끼우면 기존 계정이 하나도 이어지지 않습니다. 전원이 첫 로그인에서 새 행으로 만들어지고, 새 행은 employee_id 가 비어 있어 모두 /pending 화면으로 갑니다. 관리자가 한 사람씩 다시 연결해야 합니다.

피하는 길은 있습니다. 사람의 실체는 web_employees 쪽이고 web_users 는 로그인 껍데기이므로, 기존 web_users 행의 auth_sub 만 진짜 sub 로 갈아끼우면 employee_id 도 휴가 신청 이력도 그대로 살아남습니다.

그러려면 「누가 포털의 어느 계정인가」를 먼저 짝지어야 합니다. 포털 관리자 화면에서 사람 목록(이름·이메일·사번)을 볼 수 있으니, 지금 web_users 의 이름과 맞춰 이행 스크립트를 한 번 돌리는 방식입니다.

정하셔야 할 것

ⓐ 이행한다 — 이름으로 짝지어 auth_sub 를 갈아끼웁니다. 기존 자료가 살아남습니다. 사람 수가 적으면 손으로 SQL 몇 줄이면 됩니다.
ⓑ 새로 시작한다 — 전원이 다시 연결합니다. 지금 인원이 적고 자료가 얼마 없다면 이쪽이 단순합니다.

어느 쪽인지에 따라 아래 7번(이행) 단계가 들어가고 빠집니다.

3🔴 좋은 소식 — 세션 방식을 바꾸지 않아도 됩니다

개선요청은 서명 토큰(서버에 세션 표 없음) 방식이고, 휴가 관리는 서버 저장형 (web_sessions 표)입니다. 바꾸실 필요 없습니다.

포털이 「이 사람 로그아웃」이라고 통보할 때, 개선요청은 sessions_valid_from 이라는 칸을 새로 만들어야 했지만 — 휴가 관리는 이미 web_sessions.revoked_at 을 갖고 있습니다. 그 행에 시각을 쓰면 끝입니다. getSessionUser 의 검사도 이미 있습니다.

결론: 스키마 변경 0. session.ts 도 거의 손댈 것이 없습니다. 바꿀 것은 destroySession 이 포털 로그아웃까지 가게 하는 것 정도입니다.

덤으로 web_sessions 의 ip·user_agent·「지금 몇 곳에서 로그인해 있나」가 살아남습니다 — 개선요청은 서명 토큰으로 가면서 그걸 잃었습니다.

4🔴 지금 코드에 있는 취약점 하나 — 저희도 오늘 고쳤습니다

src/lib/auth/guards.ts 의 safeReturnTo 가 네 줄짜리 판정입니다. 저희 개선요청에도 똑같은 네 줄이 있었고, 오늘(2026-09-21) 고쳤습니다. 같은 뿌리에서 나온 코드라 같은 구멍을 갖고 있습니다.

구멍 둘

  • 🔴 제어문자를 안 막습니다. 브라우저는 주소에서 탭·줄바꿈을 조용히 지웁니다. /+탭+/evil.example 은 지우고 나면 //evil.example 이 되어 다른 사이트로 나갑니다. 눈으로 보면 슬래시가 하나뿐이라 안전해 보이는 것이 이 구멍이 오래 사는 까닭입니다
  • 🔴 한글이 든 주소면 로그인이 500 으로 죽습니다. 응답 헤더는 한글을 못 담는데 그대로 넣고 있습니다

첫 번째가 왜 위험하냐면 — 공격자가 그런 값을 붙인 회사 주소 링크를 뿌리면, 받는 사람은 진짜 통합로그인으로 정상 로그인을 마친 뒤 공격자 사이트로 떨어집니다. 거기 똑같이 생긴 로그인 화면이 있으면 「한 번 더 뜨네」 하고 비밀번호를 넣습니다.

저희가 고친 판(199줄, 시험 13개 포함)이 개선요청과 PO 두 곳에 같은 내용으로 들어가 있습니다. 그대로 가져다 쓰시면 됩니다. 순수 함수라 의존성이 하나도 없습니다.

5체크리스트 — 이 순서대로

  1. 포트를 3700 으로 옮긴다 package.json · .env · README · CLAUDE.md. 안 옮기면 계측기와 둘 중 하나가 못 뜹니다.
  2. 기존 계정을 이행할지 정한다 (0번) 이행한다면 포털 계정과 짝짓는 표를 먼저 만들어 두세요.
  3. 인증 파일을 넣는다 oidc.ts · sso-login.ts · return-to.ts · lan-address.ts · 라우트 3개. 개선요청 것을 본보기로.
  4. 환경변수를 SSO_ 이름으로 넣는다 .env.local 에. SSO_CLIENT_SECRET 은 아직 비워 둡니다.
  5. DSS 쪽에 등록을 요청한다 포털 DB 등록은 DSS 담당이 합니다. 저희에게 말씀해 주시면 등록하고 비밀키를 안전하게 전달해 드립니다. 🔴 채팅·메일로 주고받지 않습니다.
  6. 비밀키를 .env.local 에 넣고 로그인을 시험한다 포털(3100)이 함께 떠 있어야 합니다.
  7. (이행하기로 했다면) auth_sub 를 갈아끼운다 한 사람이 먼저 로그인해서 진짜 sub 를 확인한 뒤, 나머지를 맞춰 넣는 방식이 안전합니다.
  8. dev-login 을 정리한다 바로 지우지 마시고 기본 꺼짐으로 한동안 남겨 두시길 권합니다 — SSO 가 막혔을 때 들어갈 길이 하나는 있어야 합니다. 구조상 나란히 둘 수 있습니다(둘 다 createSession 에서 만납니다).
  9. (선택) 메뉴바를 붙인다 다른 시스템으로 건너다니는 띠입니다. 서브모듈 한 줄 + 설정 두 줄 + 화면 한 줄.

② 돌아갈 주소 판정 고치기 (독립적 · 지금 해도 됨)
src/lib/auth/guards.ts 의 safeReturnTo 에 보안 구멍이 둘 있다. 고쳐줘.

지금은 네 줄이다 — '/' 로 시작하는가 · '//' 로 시작하지 않는가 · 역슬래시가 없는가.

🔴 구멍 1 — 제어문자를 안 막는다.
브라우저는 주소에서 탭·줄바꿈·복귀를 조용히 지운다. "/" + 탭 + "/evil.example" 은
지우고 나면 "//evil.example" 이 되어 다른 사이트로 나간다. 눈으로 보면 슬래시가
하나뿐이라 안전해 보이는 것이 이 구멍이 오래 사는 까닭이다.
공격자가 그런 값을 ?returnTo= 에 붙인 우리 회사 주소 링크를 뿌리면, 받는 사람은
진짜 로그인을 정상으로 마친 뒤 공격자 사이트로 떨어진다. 거기 똑같이 생긴 로그인
화면이 있으면 비밀번호를 한 번 더 넣는다.

🔴 구멍 2 — 한글이 든 주소면 로그인이 500 으로 죽는다.
응답 머리말 값은 ByteString(0~255)이라 "결" 같은 글자를 그대로 넣으면 Response 를
만드는 자리에서 TypeError 가 난다. 퍼센트 인코딩으로 정규화해서 내보내야 한다.

더할 것 넷:
  1. 한 겹 푼 형태도 같은 규칙으로 검사 — "/%2F%2Fevil.example" 은 풀면 "///evil"
  2. 길이 상한 (정규화를 마친 뒤의 길이에 건다. 한글 한 글자가 9자로 부푼다)
  3. 로그인 통로 자기 참조 거절 — 무한 되돌기 방지
  4. 머리말에 실을 수 있는 형태로 정규화

판정은 import 가 하나도 없는 순수 함수로 따로 빼라(src/lib/auth/return-to.ts).
guards.ts 는 그것을 다시 내보내서 부르는 쪽을 안 고쳐도 되게 하라.

시험을 반드시 붙여라. 거절해야 할 값을 하나하나 확인할 것:
  //evil.example · https://evil.example/x · javascript:alert(1)
  "/" + 탭 + "/evil.example" · "/" + 줄바꿈 + "/evil.example"
  /%2F%2Fevil.example · /%0A/evil.example · /%09/evil.example
  역슬래시가 든 값 · 길이 초과 · 로그인 통로를 가리키는 값
그리고 한글이 든 주소가 정규화되어 나오는지(그대로 나오면 500 이 난다).

🔴 역슬래시와 제어문자를 시험 소스에 글자로 적지 마라. String.fromCharCode 로 만들어라 —
도구를 거치며 한 겹이 조용히 사라지면, 막으려던 것이 아닌 값을 시험하면서 통과한다.

  SSO_ISSUER · SSO_CLIENT_ID · SSO_CLIENT_SECRET · SSO_REDIRECT_URI
  · SSO_TX_SECRET · AUTH_SESSION_SECRET
🔴 .env.example 에 OIDC_ 접두사로 적힌 주석 줄이 있는데 이름을 SSO_ 로 바꿔라.
🔴 그 주석의 리다이렉트 경로가 /api/auth/callback 인데 규약은 /api/auth/sso/callback 이다.

## 쿠키 이름 — 🔴 쿠키는 포트를 가리지 않는다
localhost:3700 과 localhost:3000 은 같은 쿠키 통을 쓴다. 이름이 겹치면 한쪽 로그인이
다른 쪽을 덮어쓴다. 이 시스템 몫:
  leave_session (이미 있음) · leave_sso_tx · leave_service_menu
왕복 쿠키(leave_sso_tx)는 path 를 /api/auth/sso 로 좁혀라 — 나머지 요청에 안 딸려 나가게.

## 🔴 세션 방식은 바꾸지 마라
지금 web_sessions(서버 저장형)를 쓰고 있고 그대로 두면 된다. 백채널 로그아웃은
그 사람의 web_sessions 행에 revoked_at 을 쓰면 끝이다 — 그 칸도, getSessionUser 의
검사도 이미 있다. 스키마를 건드릴 필요가 없다.
바꿀 것은 destroySession 이 포털 로그아웃(/api/oidc/logout)까지 가게 하는 것뿐이다.
까닭: 이 사이트 쿠키만 지우면 포털 세션이 살아 있어, 로그인 버튼 한 번으로 누구인지
다시 묻지도 않고 들어온다. 공용 PC 에서는 그것이 곧 로그아웃이 안 된 것이다.

## 🔴 반드시 지킬 것
1. role 클레임이 **없으면 유지(KEEP)**, **모르는 값이면 거절(REJECT)**.
   없다고 거절하면 부여 행이 없는 사람이 아무도 못 들어온다. 유지하면 안전한 쪽으로
   실패하지 않는다 — 관리자를 일반으로 내리려다 이름을 잘못 적으면 관리자로 남는다.
   이 시스템의 역할 값은 MEMBER · LEAVE_ADMIN 이다.
2. 이메일이 안 오면 기존 값을 지우지 마라. 카카오에서 이메일은 선택 동의라 있다가
   없어질 수 있다 — "말하지 않았다"와 "비웠다"는 다르다.
3. 🔴 이메일로 사람을 잇지 마라. auth_sub(포털 sub) 하나로만 잇는다.
   이메일은 바뀌는 값이고, 바뀌는 값으로 사람을 이으면 언젠가 남의 계정이 된다.
4. sub 가 UUID 형식이 아니면 먼저 거절해라 — auth_sub 가 uuid 열이라 insert 가 터진다.
5. 삭제된 계정도 함께 찾아라. auth_sub 유일 색인에 조건이 없어서 못 본 척하면
   새로 만들려다 색인 충돌로 터지고, 내보낸 사람이 조용히 새 계정으로 돌아오는 것이
   더 나쁘다.
6. 로그인 시작 통로에서 메뉴바 쿠키를 지워라 — 공용 PC 에서 앞사람 목록이 뒷사람
   화면에 뜬다. 로그아웃에서도 지우되 redirect 앞에서 지워라(redirect 는 예외를 던진다).
7. 백채널 로그아웃 창구는 인증 없이 누구나 두드릴 수 있다. 서명 검증이 그 파일의
   전부다. 로그아웃 토큰에 nonce 가 있으면 거절해라 — ID 토큰을 들이밀어 남을
   로그아웃시키는 길을 막는 것이다. 끊을 게 없어도 성공(204)으로 답해라.
8. jwtVerify 는 서명·iss·aud·exp 까지만 본다. 🔴 nonce 는 따로 봐야 한다 —
   건너뛰면 예전 ID 토큰을 다시 들이미는 길이 열린 채 남는다.
9. issuer 끝의 슬래시를 떼라. "http://x/" 와 "http://x" 가 섞이면 iss 대조가
   실패하는데 원인을 찾기 가장 어려운 종류의 버그다.
10. 리다이렉트 주소를 request.url 에서 만들지 마라. 환경변수로 둬라 —
    LAN 으로 들어온 요청인데 서버 자신의 바인딩 주소(localhost)가 보이는 경우가
    실측되었다. 만들어 쓰면 "어떤 망에서는 되고 어떤 망에서는 안 되는" 형태로 실패한다.
11. JWKS 는 지연 생성 + 캐시로. 요청마다 만들면 포털을 두드린다. 그리고 파일을
    불러오는 것만으로 환경변수를 요구하면 next build 가 .env 없이 못 돈다.
12. /login 화면은 남겨라 — 거절됐을 때 이유를 보여줄 자리가 필요하고, 거기서
    자동으로 다시 보내면 무한 왕복이 된다. 다만 거절 사유를 자세히 적지 마라 —
    그러면 그 화면이 "누가 이 시스템 사용자인지" 확인해 주는 조회 도구가 된다.

## 🔴 dev-login 은 지우지 마라

두 길은 결국 createSession(userId) 하나에서 만나므로 나란히 둘 수 있다.

## 🔴 함정
- 노치 인셋은 맨 위 요소 하나만 갖는다. 머리말 안(inline)으로 들였으면 머리말이
  갖고 띠는 아무것도 안 한다. 둘 다 두면 아이폰에서 노치 높이만큼 두 번 밀린다.
- 펼친 목록은 머리말 밖으로 나온다(position:absolute). 조상에 overflow:hidden 이
  있으면 잘린다.
- 로그인 전 화면에는 넣지 마라.
- Tailwind dark: 유틸리티를 쓰지 마라. 이 묶음은 쓰지 않는다 — 쓰면 OS 가 어두운
  사람에게 "이 띠 하나만" 까맣게 뜬다.
- 클레임이 없으면 띠를 그리지 마라(쿠키도 굽지 마라). 포털에 등록되기 전이나
  그 기능이 배포되기 전에도 머리말이 예전과 같아야 한다.
- layout 이나 머리말에 "use client" 를 붙이지 마라. 딸려 오는 클라이언트 조각이
  prop 을 하나도 안 받아 서버에서 그려도 된다.
- 폰(360px)에서 머리말이 넘칠 수 있다. 시스템 이름·사용자명을 sr-only 로 감추거나
  flex-wrap 을 쓰는 식으로 자리를 만들어야 한다 — 저장소마다 답이 다르다.
- 🔴 클론할 때 --recurse-submodules 를 빠뜨리면 vendor/dss-ui 가 빈 폴더가 되어
  빌드가 크게 실패한다.
- 🔴 묶음을 먼저 올리고 이 저장소의 포인터 커밋을 올려라. 순서를 바꾸면 남의
  컴퓨터에서 체크아웃이 안 된다.

iss 대조 실패인데 원인을 못 찾겠다 issuer 끝의 슬래시. http://x/ 와 http://x 가 섞였습니다

등록 명령을 다시 돌렸더니 전 직원이 차단됐다 🔴 --open-to-all 은 다른 인자와 달리 안 주면 매번 기본값(닫힘)으로 돌아갑니다. 아이콘 하나 고치려고 재실행해도 닫힙니다. 재실행할 때마다 다시 붙여야 합니다
공용 PC 에서 앞사람의 시스템 목록이 뜬다 로그인 시작 통로에서 메뉴바 쿠키를 안 지웠습니다
도커 안에서 주소를 못 찾는다 auto 와 {lan} 은 컨테이너 안에서 통하지 않습니다 — 컨테이너 자신의 주소(172.17.x.x)를 집습니다
등록값이 깨졌다 중괄호를 작은따옴표로 감싸지 않아 셸이 건드렸습니다
localhost 로는 되는데 사내망 주소로는 안 된다 등록할 때 둘 다 넣어야 합니다. 펼쳐진 값과 문자가 달라 대조에 걸립니다
